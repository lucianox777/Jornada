# GOV-V9-100K-RECORRECURSOS-20261109 — recursos adaptativos exclusivos da campanha 24×100k

**Autoridade:** Product Owner, 09/11/2026. **Estado inicial:** DECIDIDO / implementação proposta nesta PR; **sem execução física 24×100k**. **Regra:** GOV-DOC-01. **Relações:** [#1349](https://github.com/lucianox777/Jornada/issues/1349), [#1253](https://github.com/lucianox777/Jornada/issues/1253), [ordem de execução já integrada pela #1382](Decisao_GOV_V9_100K_24_Configuracoes_Ordem_Execucao_20261109.md).

## Decisão e motivo

O PO determinou **recalcular automaticamente, para cada execução física da campanha V9 100k, o orçamento real de recursos disponível**, sem reutilizar como orçamento do fitting a memória observada no ensaio isolado do **gerador 100k**. O objetivo é deixar memória disponível para SQL e Calibrador C# coexistirem no **runner GitHub-hosted padrão**, preservando a busca e a física da campanha oficial **24/16/8**. Isto substitui **apenas** a atribuição operacional fixa de **4.096 MiB SQL / 5 GiB contêiner** daquele workflow, sem alterar o plano científico, 81 células, TF, M/U, FDR, seleção, seed, histórico, TEST ou Gold.

**Correção causal essencial:** o [run de CI 42674310513](https://github.com/lucianox777/Jornada/actions/runs/42674310513) no SHA `ccc95cc7e729c5ac540a3ae87d63f23c5c31ef83` terminou `failure` com **20 jobs `skipped` e nenhum job inicial `impact`**. Os workflows V3 direto/sobrenome falharam também com jobs pulados antes do fitting. **Não há evidência de que esses jobs tenham iniciado SQL, sofrido OOM ou sido cancelados por `--memory 5g`**. A limitação Docker só é aplicada no workflow manual 100k, **não** à CI geral. Sua causa de orquestração permanece investigação separada; não reduzir nem contornar gates de CI como correção falsa.

## Implementação específica do ensaio 100k

1. **Ordem dos steps:** autenticar SHA/master/dispatch, compilar gerador e Worker, **regerar** corpus TRAIN clean 100k seed42 e fazer *binding* do plano oficial J por SHA **antes de iniciar SQL**. A geração prévia evita sobrepor seu pico de RAM à ocupação do SQL. Depois disso, medir os recursos da **máquina deste run**, iniciar SQL descartável mascarado, reconstruir **referência TF histórica 30k** (não executar calibração 30k), medir novamente antes de iniciar os 24 fits e auditar normalmente.
2. **Novo estimador somente do run técnico:** `Solution/scripts/v9-100k-execution-resource-budget.py`, fases `plan-sql` e `before-fit`, com amostras `/proc/meminfo`, **limite/consumo cgroup quando finito** e `shutil.disk_usage` no workspace. Não lê o relatório histórico do gerador nem permite usar resultado de runner anterior como admissão física da V9.
3. **Orçamento SQL operacional de cada run:** escolher **2048 MiB** por padrão em runner padrão; **3072 MiB** somente se RAM efetivamente disponível >=18 GiB; **4096 MiB** somente se >=26 GiB. Limite Docker igual a SQL + **1024 MiB** de folga; respectivamente **3072/4096/5120 MiB**. O script de inicialização aceita os dois parâmetros **apenas se validados**; outros callers V9/30k que não configuram variáveis continuam **sem limite novo**. Os valores são **pisos de tentativa e preferência operacional para preservar RAM C#**, não estimativas científicas de memória do fitting nem otimização comprovada.
4. **Admissão antes de SQL:** host com >=12 GiB totais; disco livre >=6 GiB; memória efetiva disponível >= limite Docker escolhido + reserva de **6 GiB para o Worker e 1 GiB para SO/infraestrutura**. A reserva é uma **condição conservadora operacional**, não afirmação de pico C# medido. Em insuficiência, gravar `FAIL_CLOSED_INSUFFICIENT_RESOURCES` e **não iniciar SQL**.
5. **Admissão imediatamente antes dos 24 fits:** o recibo deve ser do **mesmo SHA**, anterior e PASS, sem permitir aumentar o orçamento com SQL já rodando; RAM efetiva disponível >=6 GiB e disco livre >=3 GiB. Insuficiência interrompe a campanha e preserva a evidência de falha; nunca se declara PASS do motor.
6. **Observabilidade:** gravar snapshots, cgroup, decisões de admissão e SQL/container MiB em JSON agregado versionado; exportar recibos sem CSV, CPFs, nomes, senhas, TEST, Gold ou dumps SQL. O relatório de recursos só demonstra **admissão**, não fitting, FDR nem cumprimento dos 24. O teste físico e o auditor de 24 configurações permanecem obrigatórios.
