## Contexto, necessidade e decisão

O passo anterior [PR #1514](https://github.com/lucianox777/Jornada/pull/1514) integrou um método **opt-in somente leitura** à classe real `ProbabilisticLinkageBatchRunner`, comprovando a leitura do vencedor V9 TF4/81 a partir de SQL `TEST_ONLY`, o grafo operacional em lotes, FS/Resolve global e os contadores com recibo **não persistido**. Não havia prova física de **transições de estados, gravação por lote, reconciliação persistida, falha parcial e rollback**. Continuar o TEST diretamente, sem ensaio transacional e sem paridade plena do legado, seria perigoso.

**Decisão incremental:** introduzir um **ledger de ensaio sintético em SQL Server descartável**, exclusivamente no banco `JornadaHarness`, com tabelas próprias `identidade.v9_synthetic_rehearsal_run` e `identidade.v9_synthetic_rehearsal_batch`, fora de `Solution/database/migrations/` e de todas as migrations de produção. **Não escrever** em `identidade.linkage_run`, `identidade.linkage_resultado`, Gold, Serving, bloqueios de publicação ou arquivo/corpus TEST selado. Não usar identidade real de cidadão nem gravar dados de nomes, CPF ou truth label. No ledger, persistir somente ID de execução sintética, modelo vencedor SHA/ID, contagens, intervalos dos IDs sintéticos, digest de IDs, hashes de grafo, decisões e agrupamentos e estados locais.

## Implementação e estados físicos

1. Instalar o schema de **teste apenas** `Solution/database/testing/20261114_V9_Synthetic_Nonpublishing_Batch_Ledger.sql` no banco efêmero `JornadaHarness` criado no próprio GitHub Actions. O script recusa explicitamente qualquer `DB_NAME()` diferente de `JornadaHarness`.
2. `V9SyntheticNonPublishingSqlLedger.PersistAsync` é **fail-closed antes de escrever**, exigindo conexão aberta `SqlConnection`, DB exato, coorte TEST pequena (2..128) com IDs únicos/positivos, `V9NonPublishingBatchExecutionReceipt` com SHA-256 de 64 caracteres, contadores fechados, `ExpectedTerminalStatus=CONCLUIDO_SEM_PUBLICACAO` apenas projetado e flags `PersistedRun=Published=ProductionBatchPipelineCertified=false`. Revalidar o modelo SQL vencedor único por `V9OperationalPinnedCohortRuntime.LoadPinnedAsync`; nunca usar modelo ATIVO nem fallback.
3. Abrir **uma única transação SQL SERIALIZABLE**: inserir run sintético `PREPARANDO`; transitar para `EXECUTANDO`; para cada lote ordenado inserir recibo (quantidade, primeiro/último ID sintético, digest SHA-256 dos IDs) e incrementar `avaliados`/`completed_batches` condicionados ao contador anterior; finalizar em `CONCLUIDO_SEM_PUBLICACAO` somente com igualdade `avaliados=elegiveis`, `completed_batches=expected_batches`, contagem real dos lotes e soma física das suas quantidades. Qualquer erro SQL ou cancelamento exige **rollback integral**: não deixar run incompleto parcialmente visível. O limite 128 é **somente desta prova**, não novo limite de execução produtiva.
4. Expor entrada distinta e opt-in na classe real `ProbabilisticLinkageBatchRunner.PersistV9SyntheticRehearsalLedgerAsync`: primeiro executa a prova SQL não publicadora existente `RehearseV9NonPublishingSyntheticTestAsync`, depois escreve os recibos no banco sintético. **O método `RunAsync` legado permanece integralmente intocado**; nenhuma leitura de Gold ou alteração de estados de produção.
5. Recibo próprio `V9SyntheticNonPublishingLedgerReceipt` diferencia explicitamente `SyntheticLedgerPersisted=true` de `ProductionLinkageRunPersisted=false`, `Published=false` e `ProductionBatchPipelineCertified=false`. O nome do estado `CONCLUIDO_SEM_PUBLICACAO` significa apenas **transição real da tabela sintética**, não da tabela produtiva.
6. Ampliar o smoke SQL real com: execução de quatro observações sintéticas e lotes de tamanho 2, leitura materializada do run em estado final, **duas** linhas de lote e contagem/sha, duplicação do mesmo ID proibida, criação proposital de trigger SQL que lança erro no **segundo** lote de outro run, prova de que **ambas** as tabelas permanecem sem registros desse run após rollback, e prova de que o recibo anterior segue intacto. Confirmar ainda que `identidade.linkage_run` e `identidade.linkage_resultado` **nem existem** no fixture. Não gravar qualquer dado do TEST 100k.
7. Incluir contrato Python no fast CI e SQL smoke em PR. Os gates devem ser `unit-runtime`, `security-guards`, `deterministic-build` 3/3, preflight Release e `one-winner-sql-smoke` real com 1/1 teste; integrar por squash merge somente quando verdes; registrar recibo PR/CI/SHA no índice.
