## Como funciona a cadeia e o controle de TEST

1. `prepare-test-100k` continua isolado e **somente** é ativado quando `test_required=true`; é dispensado quando TEST está OFF. Não existe mais uma segunda checkbox `prepare_sealed_test` que gere combinação incoerente. `expected_test_cert_sha256` e o LOCK científico continuam exigidos para preparar TEST real.
2. `physical-100k` sempre depende do estado da preparação: TEST OFF permite seu skip; TEST ON exige preparação SUCCESS. Preflight `expected_sha`, proprietário, modo DEV, SHA exato, tentativa e guard de paridade continuam fail-closed; nenhum TREINO 100k é gasto quando TEST foi solicitado antes de ser elegível.
3. `audit-100k` é job separado que exige `physical-100k.result == 'success'`, evidencia SHA/manifesto pré-auditoria íntegro e produz o mesmo audit científico. O skip de preparação TEST opcional não bloqueia AUDIT.
4. `validation-100k` depende incondicionalmente de **AUDIT SUCCESS com finalistas aptos**. Quando não houver nenhum finalista, **não existe modelo a validar**: a condição `has_finalists=true` bloqueia a VALIDATION; novo step `V9_MANDATORY_VALIDATION_NO_FINALISTS` faz o job AUDIT falhar explicitamente após registrar o status científico, para que o workflow seja **FAILURE** e nunca apresente SUCCESS com VALIDATION SKIPPED. Isso é distinto de permitir desmarcar VALIDATION. A VALIDATION sempre permanece parte obrigatória do protocolo quando a campanha produz finalistas.
5. `test-100k` depende de `validation-100k=success` e `prepare-test-100k=success`, e roda **somente** com `test_required=true`; nunca acessa TRAIN/VALIDATION cruas. `always() && !cancelled()` no gate evita propagação indevida de skip, preservando resultados positivos explícitos e sem permitir uma execução após cancelamento do workflow.
6. Todos os `timeout-minutes` explícitos no workflow TF4/324 permanecem removidos, conforme `GOV-V9-TF4-JOBS-INDEPENDENTES-TIMEOUT-NATIVO-20261114`; a plataforma GitHub Actions governa o tempo máximo do job. Timeouts de SQL/IO para resiliência não são abrangidos pela decisão.

## Testes de integração que devem anteceder 100 mil

O novo workflow `.github/workflows/v9-tf4-chain-integration-smoke.yml`, acionado em PR/dispatch, cria **três runners GitHub-hosted independentes** com ligações `needs` equivalentes à produção. Na execução default TEST OFF, `prepare-test-optional` é SKIPPED propositalmente; o TRAIN sintético envia um artefato com o **mesmo contrato `v9-v3-four-name-100k-preaudit.py`** (SHA-256, allowlist, run ID e commit SHA); o AUDIT sintético recebe/verifica os bytes e publica um recibo de ponte **expressamente não científico**; a VALIDATION sintética valida outro download, SHA/correlação e a conclusão da cadeia. Um job TEST **simulado** opcional pode ser ligado na execução manual do smoke para comprovar somente o controle DAG, sem coorte TEST nem credenciais.

Testes Python offline adicionam **positivos e negativos**: origem divergente, run ID trocado, byte adulterado, arquivo CSV imprevisto, recibo AUDIT adulterado, campos de falsa execução científica, skip opcional, sucessos explícitos, gate TEST/LOCK e ausência de `timeout-minutes`. O gate de CI rápida passa a chamar esses testes e corrige o filtro NUnit para o **nome atual** do teste ETA `Physical_progress_forecast_is_informational_without_local_deadline` (antes o filtro antigo já não selecionava teste após a alteração em #1526).

**Limite das evidências:** esse smoke prova **orquestração GitHub de três jobs e transferência de artefatos sintéticos**, **não** reproduz fitting das 324 hipóteses, auditoria científica, 100k holdout, SQL real, bloqueio dinâmico do TEST, igualdade de JSON operacional, paridade do Runner ou prazos do 100k. ## Pendências para TEST com exatamente o mesmo contrato de produção

**Problema de formato confirmado:** o TEST recebe um arquivo canônico `<sha>.fitted.json` (snapshot `V9_FITTED_SNAPSHOT_V3`), que pode ser convertido losslessly para SQL V9 `TEST_ONLY`. No entanto, o Runner produtivo atual **não executa esse mesmo JSON**: o caminho padrão lê `identidade.modelo_linkage` e tabelas relacionadas; a ponte V9 SQL existente é opt-in, e a execução plena `ProbabilisticLinkageBatchRunner.RunAsync` com o vencedor V9 não possui prova operacional E2E. **Logo “mesmo JSON de produção” ainda não está demonstrado; a existência de um conversor ou de SHA verificado não basta.** O requisito do PO só fica atendido se TEST e produção carregarem um **mesmo contrato de modelo executável** (se JSON canônico for obrigatório, adicionar seu loader operacional governado; jamais substituir por um SQL parcial), com igualdade de todos os parâmetros, TF4/81 células, blocking, scorers, Resolve, agrupamento e resultado final.

**Além do JSON faltam:** (a) binding do único vencedor V9 no schema operacional sem pseudo-modelo legado nem violação de FKs; (b) execução real `RunAsync` em banco integral descartável e paridade por candidato/observação/cluster e todos TF0/TF ativo, batches, transações, falha/replay; (c) prova de Publish=false e nenhuma mudança em Gold/Serving, auditoria do caminho de produção; (d) LOCK/pre-registro da coorte TEST independente e uso único global entre tentativas, certificado/chaves de segurança configurados, isolamento de gabarito antes do scoring e recibos duráveis sem PII; (e) VALIDATION física efetiva com finalistas e seleção de um único vencedor; (f) gates da campanha 100k e governança de publicação/DT-15 separados. Issues [#1488](https://github.com/lucianox777/Jornada/issues/1488) e [#1478](https://github.com/lucianox777/Jornada/issues/1478) continuam abertos. Não remover `V9_TEST_PRODUCTION_FORMAT_PARITY_NOT_IMPLEMENTED` para facilitar o smoke.
