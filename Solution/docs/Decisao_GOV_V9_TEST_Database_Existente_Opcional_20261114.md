## Contexto e razão da mudança

No [workflow manual V9 TF4/324](../../.github/workflows/v9-v3-four-name-100k.yml), `test_required` é um único checkbox. A VALIDATION agora gera um modelo V9 canônico `<winnerSha>.operational.json` (GOV-V9-VALIDATION-ARQUIVO-OPERACIONAL-FINAL-TEST-NOME-20261114). Antes desta decisão, `--v9-independent-test` aceitava somente o nome do arquivo e estava rigidamente associado a `JornadaHarness`, à coorte sintética selada e a métricas calculadas com gabarito. O PO solicitou escolher o database explicitamente, *sem regenerar coorte sintética*, preservando o arquivo de parâmetros vencedor e o modo padrão.

## Decisão operacional aprovada e desenho

1. **Único TEST opcional, fonte alternativa explícita.** Adicionar input opcional `test_database` (string vazia por padrão) ao workflow e argumento `--test-database <nome_db>` ao `--v9-independent-test <SHA>.operational.json`. O JSON continua sem endereço, banco ou credenciais. Uma escolha explícita de DB exige `test_required=true`; não se inicia fluxo TEST quando checkbox estiver desmarcado.
2. **Sem nome de DB (padrão):** manter `prepare-test-100k`, geração sintética DEMOGRAPHIC_PRIMARY limpa de 100K, seed/certificado pré-fixados, CMS lacrado, LOCK/tag global one-use, TEST privado em `JornadaHarness` descartável, sem alterações dos parâmetros. **A execução está atualmente bloqueada** pelo gate `V9_TEST_PRODUCTION_FORMAT_PARITY_NOT_IMPLEMENTED` até a prova completa `ProbabilisticLinkageBatchRunner.RunAsync`; esta decisão não o relaxa.
3. **Nome de DB informado:** executar **preflight antes de TRAIN 100K**, com conexão e login SQL independentes de acesso somente SELECT; verificar nome do banco, esquema real `silver.pessoa_observacao` + `ref.gestor`, acesso SELECT e ausência de papéis/permissões de gravação. O segredo `V9_EXTERNAL_TEST_READONLY_CONNECTION` nunca é enviado aos jobs TRAIN/AUDIT/VALIDATION. O database especificado sobrepõe **somente** `InitialCatalog` da conexão do segredo e não altera o JSON vencedor.
4. **Acessar dados existentes, SEM criar sintéticos:** após VALIDATION SUCCESS com vencedor, executar `test-database-readonly` em runner **privado controlado pelo PO**, etiqueta `[self-hosted, v9-private-readonly]`. Fazer somente SELECT de `pessoa_observacao_id`, `gestor`, nome, nome da mãe e data nascimento, para fontes sem CPF; nunca solicitar gabarito/PII em logs/artefatos. O corpus não é persistido, não se invoca gerador/selador, não se cria banco/tabela nem se executa `--v9-convert-winner-operational` no database informado.
5. **Execução V9 não publicadora:** carregar exatamente o `<winnerSha>.operational.json`, projetar *em memória* os passes de blocking congelados TF4/81, construir **grafo completo dentro do universo elegível**, recusar fanout excessivo e truncamento, executar o scorer/Resolve e agrupamento BLIND congelados pelo `V9FrozenSourceResolveReplay.ReplayTest`. **Arestas externas em memória não são equivalentes à materialização SQL do Runner produtivo**; output é **DIAGNÓSTICO OPERACIONAL, NÃO TEST CIENTÍFICO E2E COM PARIDADE CERTIFICADA**. Sem gabarito independente não inventar TP/FP/FN, FDR, precisão, recall, IID ou publicação.
6. **Limites de segurança mensuráveis:** universo sem CPF de 2 a 100.000 registros. Se exceder 100K, **falhar sem amostragem**, exigindo ajuste consciente posterior; até 2 milhões de arestas, 2 milhões de chaves/expansões e 4 milhões de incidências de buckets (inclusive pares intragestor), falhar quando ultrapassar, nunca truncar arestas; banco deve ter nome `[A-Za-z][A-Za-z0-9_]{0,127}`, não sistema nem `JornadaHarness`. Credenciais SELECT-only, `ApplicationIntent=ReadOnly`, pool desligado, nenhum write em SQL ou Gold/Serving. Não publicar linhas, nomes, chaves, SQL connection string, grupos ou decisões individuais; apenas contagens e SHA de diagnóstico no artefato `external-database-test.json`.
7. **Gates do workflow:** `prepare-test-100k` e `test-100k` continuam exclusivos do modo sintético. O modo DB usa `test-database-preflight` + `test-database-readonly`, exigindo VALIDATION SUCCESS e mesmo SHA do vencedor, não pode nem abrir corpus científico selado. `e2e-closeout` exige sucesso dos jobs específicos e reporta estado distinto `E2E_CORE_WITH_EXISTING_DB_READONLY_DIAGNOSTIC_NOT_SCIENTIFIC_TEST`, sem converter o diagnóstico em TEST científico PASS. Nenhum `timeout-minutes` adicional nos jobs; GitHub gerencia os limites de runner.
8. **Antes de gastar 100K:** executar CI rápida obrigatória, NUnit do nome/segredo/DB/arestas sem verdade, contratos Python de bifurcação, teste GitHub de integração sintético TEST OFF e SQL smoke operacional não publicador. O teste real com banco indicado requer previamente **runner privado configurado, segredo SELECT-only e conectividade**, além do SHA exato da master e `security_preflight_approved`. Se indisponíveis, preflight falha/bloqueia TRAIN, sem gasto físico.

## Precedência, impactos e riscos

**Complementa sem substituir** GOV-V9-CADEIA-OBRIGATORIA-E2E-PREFLIGHT-20261114 (TRAIN→AUDIT→VALIDATION sempre vinculados), GOV-V9-TF4-JOBS-INDEPENDENTES-TIMEOUT-NATIVO-20261114 e GOV-V9-VALIDATION-ARQUIVO-OPERACIONAL-FINAL-TEST-NOME-20261114; mantém `test_required` como único checkbox de TEST e acrescenta apenas a escolha de origem. Mantém GOV-V9-TEST-ONE-USE, GOV-DOC-01 e as issues [#1488](https://github.com/lucianox777/Jornada/issues/1488) e [#1478](https://github.com/lucianox777/Jornada/issues/1478).

**Benefícios:** testar parâmetros congelados em uma base já populada, sem geração de dados; separar banco e modelo; evitar correr 324 hipóteses quando DB não está disponível, credencial não é SELECT-only ou esquema não é compatível.

**Riscos e limites não ocultos:** (a) uma base real pode conter cidadãos/PII e acessos privados — daí runner privado e segredo com menor privilégio; (b) um DB existente pode não ter gabarito nem independência, então nunca equiparar o diagnóstico a TEST científico; (c) sem certificado de paridade do `ProbabilisticLinkageBatchRunner.RunAsync`, esse resultado não homologa produção, mesmo usando o mesmo JSON de parâmetros; (d) o universo elegível sem CPF precisa estar íntegro até 100K; se houver mais, abortar sem truncar; (e) as assinaturas de blocking são construídas no memory runner a partir do fit, não de SQL produtivo, e portanto são diagnóstico; (f) a origem externa pode mudar entre preflight e execução, exigindo nova prova se homogeneidade temporal for requerida. Nenhuma execução real foi iniciada aqui.

**Critérios de aceite:** compilação, testes adversariais de segurança/CLI/mesmo JSON, CI 3/3, cross-job sintético e SQL smoke, PR integrada, índices sincronizados; somente depois uma execução TEST opcional explicitamente configurada por PO, no banco próprio de ensaio com acesso SELECT-only — não tocar produção sem autorização e ambiente protegido.

## Observação de nomenclatura

`test_database` seleciona o **database existente que fornece os registros de observações**, e portanto é a fonte de leitura do diagnóstico operacional. Ele não é embutido nem gravado em `operational.json`. O resultado gerado descreve explicitamente `EXISTING_DATABASE_NO_SYNTHETIC_GENERATION`, `generatedSyntheticData=false`, `goldTruthAvailable=false` e `productionRunnerFullPipelineParityCertified=false`.
