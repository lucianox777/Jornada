# GOV-V9-GITHUB-STANDARD-100K-OPT-20261109 — executar no GitHub padrão sem servidor do PO

**Autoridade:** Product Owner, 09/11/2026. **Estado:** IMPLEMENTADO via PR #1379, master `b4902dbe0f0ee815eafd4aa48fa216be23c9c382`; gerador sintético 100k PASS no runner padrão (run 42664056609), **sem campanha física V9 SQL+24 opções nem certificação**. **Regra:** GOV-DOC-01.

## Decisão e contexto

O PO confirmou a estratégia: **otimizar o ensaio técnico de 100 mil identidades para executá-lo nos próprios runners padrão do GitHub Actions, evitando criar, contratar ou administrar máquina externa**. Para repositórios públicos, o GitHub documenta `ubuntu-24.04` com **4 vCPU, 16 GB de RAM e 14 GB SSD** e execução padrão gratuita. Fonte: https://docs.github.com/en/actions/how-tos/write-workflows/choose-where-workflows-run/choose-the-runner-for-a-job

A PR #1378 estabeleceu a alternativa self-hosted por considerar bloqueadores os requisitos conservadores da campanha original de 24 GiB RAM e 40 GiB de disco. Esses requisitos não são limite intrínseco validado para o Calibrador nem prova de capacidade realmente necessária. **Esta decisão substitui o runner autohospedado como caminho preferencial**; ela **não** afirma que SQL+24 hipóteses já cabem no GitHub padrão. Caso não caibam após evidências, mudanças de código/memória devem ser projetadas, medidas, verificadas contra regressões e aprovadas individualmente. Nenhuma VM externa foi provisionada; a alternativa self-hosted fica somente como contingência futura condicionada ao PO e à avaliação do risco em repositório público.

## Etapas técnicas e limites

**1. Manter ciência imutável.** Preservar o único `plan.json` oficial com as mesmas **24 hipóteses V9 multiparâmetro** (16 witness/diagnóstico e 8 candidatas CP), TF histórico IBGE/seed42 de 30k como referência **não limitadora de população**, corpus técnico 100k seed42 com hash próprio, 81 células, M/U/TF, blocking, limiares, FDR, ordem e isolamento TRAIN/VALIDATION/TEST. **Não cortar dados nem opções** para fazer o teste caber e não tratar SCALE V8 como prova V9. A decisão de 05/11 — **sem teto universal do número de registros** — continua vigente.

**2. Alterar apenas infraestrutura de execução.** O workflow `v9-multiparameter-100k-technical.yml` passa a usar o GitHub-hosted `ubuntu-24.04`, mantendo `workflow_dispatch` somente do proprietário, `expected_sha` master exato, `security_preflight_approved` e sem eventos push/PR. Os novos gates de recursos verificam os valores **realmente presentes** na VM, com relatórios JSON: antes de SQL, RAM total >=12 GiB e disco livre >=6 GiB; antes do fit, RAM disponível >=4 GiB e disco livre >=3 GiB. Esses números são **pisos de admissão de tentativa**, não garantia de sucesso nem mudança científica. Se falhar por recursos, parar com FAIL, nunca marcar 100k PASS.

**3. Proteger RAM para o C# em coexistência com SQL.** Somente no novo modo 100k GitHub padrão, iniciar SQL Server 2022 descartável com `MSSQL_MEMORY_LIMIT_MB=4096` e contêiner `--memory 5g`; SQL mantém mais de 1 GiB para processo/contêiner, deixando memória host para SO e worker C#. Essa limitação é **operacional**, não altera qualquer valor de `plan.json`, fit, TF/M/U ou o formato da saída. O script de bootstrap compartilha a guarda opcional: quando a variável não está definida, **todas as campanhas 30k permanecem como antes**. A recomendação Microsoft distingue limite de SQL do cgroup, exige folga entre ambos e desaconselha container sem hard limit: https://learn.microsoft.com/en-us/sql/linux/configure/performance-best-practices-sql-server-memory

**4. Medir na máquina real antes da física.** O workflow isolado `v9-github-standard-runner-100k-resource-profile.yml` é acionado exclusivamente por **push da master em arquivos específicos deste perfil** e executa **somente a geração do corpus sintético 100k e verificações de hash/manifeste**. Não inicia Docker/SQL, não ajusta modelo, não acessa TEST/Gold, não baixa artefato de histórico, não publica dados por pessoa e não executa 24 fitting options. Registra apenas pico RSS do processo gerador (GNU time), tamanho lógico de arquivos, RAM/disco do runner e SHA dos arquivos produzidos. Evidência suficiente para separar a capacidade de gerar 100k da capacidade de executar o motor V9 completo. **Não é prova da #1349**.

**5. Provar antes de concluir.** Testar negativamente falta de RAM/disco, execução apenas manual do ensaio completo, checks de SHA e nenhum novo gatilho de física. CI da PR e da master no SHA exato e observação do perfil real. **A campanha completa continua BLOQUEADA pelo preflight #1253** (log histórico de senha SQL efêmera e retenção/reutilização), mesmo que o perfil de geração passe. Somente após auditoria de segurança e autorização poderá haver `workflow_dispatch` de V9 100k técnica, com auditoria de 24/24 hipóteses, TP/FP/FN, FDR observado sem certificação, p95, RAM, disco (escopo declarado), SHA, relatório GOV-DOC-01 e fechamento de #1349. Não usar TEST cego, Gold, DT-15, HML/Produção ou ativação.

## Impactos, precedência e rastreabilidade

- **Substitui operacionalmente** a exigência de `[self-hosted, linux, x64, jornada-v9-100k-ephemeral]` da #1378, sem declarar erro científico ou reduzir exigência de segurança.
- **Preserva** os controles #1253, separação científica, 30k congelado, release v9.0.0, decisão de número ilimitado de registros, respeito ao plano oficial e conceito de teste manual V9 100k.
- **Não gera custo de infraestrutura própria**; GitHub-hosted padrão em repositório público é gratuito segundo GitHub Docs. O uso de Actions e retenção de artefatos deve continuar monitorado conforme limites vigentes.
- **Evidência pretendida:** nova PR (código e testes), checks SHA, run pós-merge do perfil 100k *somente gerador*, relatório com PASS/FAIL/PENDENTE por componente. **Não afirmar resultado do motor antes do run técnico real**.
