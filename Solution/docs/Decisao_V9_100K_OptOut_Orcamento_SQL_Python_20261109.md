# GOV-V9-100K-SQL-PY-OPTOUT-20261109 — opção manual de dispensar dimensionamento Python de memória SQL

**Autoridade:** Product Owner, 09/11/2026. **Estado:** autorizado como opção a implementar em PR; **sem execução 100k comprovada**. **Política:** GOV-DOC-01.

## Decisão, contexto e justificativa

O PO deseja executar o Calibrador V9 com 100.000 identidades sintéticas sem obrigar que o script Python `Solution/scripts/v9-100k-execution-resource-budget.py` determine o limite de memória do SQL Server. Essa decisão surge após a retirada da V9-Lite: a V9 completa, com governador C# e `MaximumParallelRuleSets` (0 AUTO, valores positivos explícitos), permanece como única arquitetura. A capacidade futura de aumentar vCPUs/RAM no data center motiva testar opções de provisionamento de SQL sem associar essa decisão a qualquer alteração na ciência, no corpus ou no motor de calibração.

**Fronteira técnica:** o Python **não altera a memória do SQL Server diretamente**. No workflow manual `.github/workflows/v9-multiparameter-100k-technical.yml`, calcula dois limites e exporta `V9_SQL_MEMORY_LIMIT_MB` e `V9_SQL_CONTAINER_MEMORY_MB` via `GITHUB_ENV`. O `Solution/scripts/v9-tf-start-disposable-sql.sh` então aplica `MSSQL_MEMORY_LIMIT_MB` e `docker run --memory`. Se tais variáveis não forem definidas, o bootstrap SQL já inicia sem teto imposto por esse workflow. No uso local direto de `--v9-calibrate`, o Worker C# **não invoca esse Python**.

## Comportamento configurável (somente workflow manual 24×100k)

Adicionar entrada booleana de `workflow_dispatch` **`disable_python_sql_budget`**, padrão `true`, espelhada na variável do job `V9_100K_DISABLE_PYTHON_SQL_BUDGET`.

- **`false` (alternativa para dimensionamento adaptativo):** executar `v9-100k-execution-resource-budget.py` nas fases `plan-sql` e `before-fit`, selecionar o teto SQL pelo orçamento real (2048/3072/4096 MiB), aplicar limites Docker/SQL já existentes, registrar recibos originais e executar o C# normalmente.
- **`true` (PADRÃO decidido pelo PO em 09/11/2026):** **não executar esse Python em nenhuma das duas fases** e **não exportar valores** para `V9_SQL_MEMORY_LIMIT_MB`/`V9_SQL_CONTAINER_MEMORY_MB`. O bootstrap SQL efêmero mantém suas proteções de senha/loopback, porém deixa o SQL e Docker com os limites de memória padrão do runtime; não interpretar isso como memória infinita nem como performance garantida.
- **Segurança do opt-out:** substitui somente a admissão de recursos do Python por verificações mínimas em Bash sobre `MemTotal`, `MemAvailable`, eventual teto/uso cgroup v2 e disco: antes do SQL, host >=12 GiB, RAM efetiva livre >=10 GiB e disco >=6 GiB; antes do fitting, RAM efetiva livre >=6 GiB e disco >=3 GiB. Valores ilegíveis/insuficientes **falham fechados**, não fazem fitting e geram evidência agregada `V9_100K_SQL_MEMORY_NATIVE_PREFLIGHT_V1`, sem segredos. O Bash rejeita variáveis SQL limitadoras presentes para não mascarar falsa desativação.
- **Invariantes:** SHA exato da master, `workflow_dispatch`, ator proprietário, confirmação de preflight de segurança, `JornadaHarness` descartável, credential mascarada e limpa, corpus clean 100k seed42, pin oficial, 24/16/8 opções, V2/V3/misturas/TF/M/U/FDR/81 células, TEST e Gold ausentes, nenhuma certificação, publicação ou ativação. Governador **interno C# permanece ativo**; o trabalho ainda pode falhar por pressão de memória ou tempo.

## Precedência, riscos e rastreabilidade

Esta opção **especializa somente a política de SQL externo do 100k** em [GOV-V9-100K-RECORRECURSOS-20261109](Decisao_V9_100K_Orcamento_Adaptativo_Execucao_20261109.md), cujo dimensionamento Python segue obrigatório no modo padrão. **Não revoga** [GOV-V9-CALIBRADOR-RECURSOS-INTERNOS-20261109](Decisao_V9_Orcamento_Adaptativo_Interno_Modo_Calibracao_20261109.md), nem os gates científicos e a política de segurança. A [issue #1253](https://github.com/lucianox777/Jornada/issues/1253) permanece aberta; `security_preflight_approved=true` só pode ser fornecido após a verificação competente, não automaticamente por este opt-out. Esse registro não autoriza executar campanha agora.

**Risco operacional explícito:** sem teto `MSSQL_MEMORY_LIMIT_MB`/Docker, SQL pode consumir mais memória e prejudicar o Worker; cgroup, kernel, SQL e Docker ainda impõem seus próprios limites. Monitore RSS, memória, disponibilidade SQL e tempos. O preflight é limiar de **admissão**, não garantia de conclusão 100k; execução manual deve registrar resultados e FAIL de forma íntegra.

**Implementação proposta:** branch `feature/v9-100k-disable-python-sql-budget-20261109`, a integrar somente com validação dos gates e aprovação da mudança. Nenhum benchmark Lite, TEST/Gold ou modelo de produção é alterado.

## Decisão superveniente do PO — 09/11/2026, três ajustes aprovados

**Prioridade funcional e precedência sobre as descrições antigas acima:**

1. **SQL sem Python por padrão:** `disable_python_sql_budget=true` passa a ser o valor padrão no formulário manual da campanha V9 24×100k. O Bash de admissão continua medindo capacidade do host/cgroup/disco, mas não aplica `MSSQL_MEMORY_LIMIT_MB` nem `docker --memory`; o SQL conserva os limites nativos da infraestrutura. O ajuste Python `v9-100k-execution-resource-budget.py` continua disponível **apenas quando `disable_python_sql_budget=false`**. Não desabilitar outras tarefas Python de binding/auditoria.
2. **Logs completos em desenvolvimento local:** exceções com mensagem, tipo e stack, eventos de host/Worker e fase são exibidos integralmente no terminal **somente** quando `DOTNET_ENVIRONMENT=Development`, o `ASPNETCORE_ENVIRONMENT` (se definido) também é Development, e `CI`/`GITHUB_ACTIONS` estão ausentes; os modos `JORNADA_RUNTIME_MODE=PROD/PRODUCTION` bloqueiam diagnóstico. A escrita reservada `calibrador.log` continua com código seguro, mesmo no DEV, para não contaminar artefatos. **Atenção:** log detalhado pode conter dados privados e credenciais; usar exclusivamente terminal privado e dados sintéticos. GitHub Actions e produção mantêm apenas código seguro e não executam formatters de exceções.
3. **100k com paralelismo da V9 completa:** a campanha técnica manual deve vincular `MaximumParallelRuleSets=0` (AUTO) ao **plano técnico de execução** por `v9-scale-100k-technical-plan.py --parallelism auto`. O recibo registra `runtimeParallelismMode=AUTO_0` e `historicalMaximumParallelRuleSets`. O campo é **exclusivamente operacional**; o binding reconstitui o plano científico histórico sem diferença nas opções V2/V3/TF/M/U/FDR e prova que somente proveniência do corpus e esse campo operacional mudaram. O governador C# calcula o paralelismo real conforme CPUs e RAM e registra `effectiveParallelism`. **AUTO pode resultar em um só worker se a capacidade real não permitir mais; não prometer velocidade multiplicativa.**

**Execução/resultado:** PO solicitou rodar o calibrador no SHA da master e analisar evidências; porém, a edição e o merge do código **não são** calibração. É obrigatório o `workflow_dispatch` feito pelo proprietário com SHA master exato e preflight de segurança `security_preflight_approved=true`, depois de tratar pré-requisitos da [issue #1253](https://github.com/lucianox777/Jornada/issues/1253). Não forçar liberação de segurança e não criar disparo automático de 100k. O workflow deve gerar audit JSON e artifacts SHA-bound; até executar, o resultado 100k V9 multiparâmetro é **PENDENTE**, nunca declarar PASS.

**Riscos:** deixar SQL sem teto externo pode provocar pressão de RAM/OOM e reduzir `effectiveParallelism`, independentemente das vCPUs; log completo local pode revelar informações sensíveis, por isso não é habilitado em CI/Produção. A alteração **não ressuscita V9-Lite**, não ativa modelo, não executa TEST/Gold e não altera governança/DT-15. **GOV-DOC-01**: decisão vigente supera o padrão `false` anteriormente aprovado no mesmo documento; os índices devem sinalizar explicitamente a precedência.
